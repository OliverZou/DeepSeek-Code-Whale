超 350 万浏览：一文讲清近期 AI 圈爆火的 Loop Engineering 到底是什么

2026-06-10 13:00·老年人学AI
作品声明：个人观点、仅供参考

这两天如果你关注 AI 圈，大概率会反复看到一个新词：Loop Engineering（循环工程）。

谷歌云 AI 负责人 Addy Osmani 6月9日发表的长文经过 1 天发酵已经超过 109 万浏览；

6月9日发表，1天达到109万热度

Anthropic 工程师 Lance Martin 在 6 月 10 日 凌晨 Claude 发布 Fable5 后发表写的 Fable 5 循环实验，发布约 10 小时就达到 60 万浏览。

6月10日凌晨在 claude 发布 Fable5 后发表


另一篇面向 AI 工程师的通俗解读，不到1天，已经冲到 181 万浏览。

不到1天 181万

三篇文章合计已经超过 350 万浏览，而且它们并没有在讨论同一款产品。

一篇讲 Claude Code 和 Codex 里的工程拼图，一篇讲 Fable 5 怎样在循环里自我纠错和积累记忆，另一篇把整套方法拆成发现、规划、执行、验证和迭代。

它们最后指向了同一个变化：

过去，我们不断给 Agent 发下一条提示词；现在，一批 AI 工程师开始设计一套系统，让系统自己寻找下一步、调用 Agent、检查结果，不合格就继续修改，达到标准以后再停下来。

很多人看到“循环工程”四个字，会以为这又是给旧东西换了一个新名字。把三篇文章放在一起看，我的判断是：这个词可能会继续变化，但它描述的工作方式已经出现了。

以前你自己就是循环，只是没有意识到

先别急着记新概念，回想一下我们平时怎么用 Claude Code、Codex 或 Hermes。

你先说需求，Agent 修改代码。你检查以后发现不对，再告诉它哪里要改；测试失败了，把报错贴回去；它修完以后，你再提醒它补测试、看差异、确认有没有遗漏。

把这个过程压缩一下，就是：

你提出目标
→ Agent 执行
→ 你检查结果
→ 你指出问题
→ Agent 再修改
→ 你再次检查
→ 直到可以交付

Agent 虽然在干活，真正负责推进任务的人仍然是你。你既是调度员，也是检查员，还是那个不停发送“继续”的人。

Loop Engineering 想做的，是把这套人工推进过程写进系统：

设定目标
→ 系统发现下一步
→ Agent 制定计划并执行
→ 测试或验证 Agent 检查
→ 不通过就把反馈送回去
→ 达标后停止或交给人确认

提示词依然存在，只是发出下一条提示词的人，开始从用户变成循环本身。

一条循环真正要跑的，其实只有 5 步

第三篇高热文章把 Loop Engineering 压缩成了 5 个步骤。这个框架很值得记下来，因为无论是写代码、做研究，还是整理内容，骨架都差不多。

步骤

大白话解释

常见依据

Discover（发现）

先弄清楚现在最该处理什么

失败测试、待办、Issue、用户反馈

Plan（规划）

决定先做哪一步，怎样做

任务清单、修改范围、风险判断

Execute（执行）

调用工具把工作真正做出来

代码、文档、报告、配置修改

Verify（验证）

对照标准检查结果是否合格

测试、评分表、规则、人工检查点

Iterate（迭代）

不合格就根据反馈继续修正

报错、差异、审查意见、下一轮计划

通过验证就交付，没有通过就重新进入下一轮。

这里最容易被忽略的是 Verify（验证）。不少所谓“自动循环”，只有执行和重试，没有清楚的验收标准。Agent 看见程序没报错，就宣布完成，实际业务目标可能根本没有做到。

所以，搭循环以前先问一句：

“我凭什么判断这件事真的完成了？”

能写成测试的，尽量用测试；能写成数字的，尽量给数字；能列成检查清单的，就不要只写“效果要好”“质量要高”。

循环能不能稳定，靠的是 5 块拼图和 1 个记忆本

Addy Osmani 把可用的循环拆成 5 块主要能力，再加一份放在对话外面的长期记忆。

第一块是 Automation（自动化）。它负责定时或按事件启动任务。比如每天早上检查失败测试，每次提交后扫描风险，或者每隔一段时间整理新的 Issue。

第二块是 Worktree（独立工作树）。多个 Agent 同时修改同一个项目时，各自在独立目录和分支里工作，避免彼此覆盖文件。

第三块是 Skill（技能）。项目规则、启动方法、测试方式和历史经验被写下来，Agent 每轮开始时直接读取，不必重新猜一遍。

第四块是 Plugin（插件）和 Connector（连接器）。它们让循环能够读取代码仓库、任务系统、数据库和通知渠道。没有连接器，Agent 只能在本地文件里打转；有了连接器，它才能更新任务、提交结果和发送通知。

第五块是 Sub-agent（子 Agent）。一个 Agent 负责探索或执行，另一个 Agent 负责检查。写答案的人不再自己给自己判满分。

最后还要有一个记忆本。它可以是 LOOP.md、Kanban、Issue 或数据库，至少要记住：

  • 当前目标是什么。
  • 已经尝试过什么。
  • 哪些方法失败了，为什么失败。
  • 现在卡在哪里。
  • 下一轮应该做什么。

Addy 有一句话很形象：模型会忘记，仓库不会忘记。

真正能跨小时、跨天继续工作的循环，靠的通常不是无限延长聊天记录，而是把状态和经验写到外面。

Fable 5 的实验说明：强模型开始能在循环里自己变好

如果说 Addy 的文章是在搭框架，Lance Martin 的文章则拿 Fable 5 做了两组更具体的实验。

第一组是 Self-correction loop（自我纠错循环）。

他给 Agent 一份包含 9 项可检查标准的 Rubric（评分标准），让 Fable 5 修改训练代码、启动实验、读取分数、决定下一次实验，再由独立的 Grader Agent（评分 Agent）判断是否达到停止条件。

一次任务最长运行了 8 小时。在这个特定的 Parameter Golf 实验里，Fable 5 对训练流程的改进幅度约为 Opus 4.7 的 6 倍。

这个数字不能直接理解成所有任务都提升 6 倍。更值得注意的是它的工作方式：Fable 5 更愿意尝试结构性变化，遇到一次退步也没有立刻放弃，而是继续读取结果、调整方向，再寻找更大的收益。

第二组是 Memory loop（记忆循环）。

有效记忆并不是把失败随手记下来，而是完成下面这条链路：

失败并记录
→ 调查失败原因
→ 验证自己的猜测
→ 把确认过的经验提炼成规则
→ 下一次任务先读取规则

在他测试的跨会话数据库任务里，Fable 5 表现较好的运行，验证覆盖达到 30 个问题中的 22 个，并把经验提炼成后续可以重复使用的规则。

这两组实验给循环工程补上了很关键的一块：模型不只要能连续工作，还要能从环境反馈中纠错，并把验证过的经验带到下一次任务。

一个 Agent 和一支小队，区别不在数量

Loop 可以只有一个 Agent，也可以是一支 Agent 小队。

Single-agent loop（单 Agent 循环）适合边界清楚的小任务。一个 Agent 自己发现、规划、执行、验证，再根据结果重做。

Fleet loop（Agent 小队循环）则由调度 Agent 管目标，再把工作交给不同角色：

调度 Agent：拆分目标、安排顺序、汇总状态
探索 Agent：查资料、阅读代码、寻找原因
执行 Agent：完成修改或产出
验证 Agent：对照标准检查结果
整理 Agent：汇总证据、记录状态、准备交付

Agent 越多并不代表越厉害。任务依赖关系没有理清时，多 Agent 只会更快地产生冲突、重复劳动和更高费用。

一个实用判断是：

  • 彼此独立、可以同时完成的任务，适合并行。
  • 前一步会决定后一步输入的任务，适合顺序执行。
  • 执行和验证最好分开，避免原 Agent 顺着自己的思路自证正确。

Worktree 解决的是文件冲突，清楚的角色和验收标准解决的才是思路冲突。

开放循环看起来很酷，封闭循环更适合现在

Rahul 的文章还区分了 Open Loop（开放循环）和 Closed Loop（封闭循环）。这可能是当前最实用的一组判断。

开放循环给 Agent 很大的探索空间。你只给目标，具体尝试什么、调用多少工具、做多少轮实验，由系统自己决定。

它适合研究、探索和答案未知的问题，但也最容易消耗 Token、跑偏和产生大量看似丰富的结果。

封闭循环会提前写清楚范围、允许动作、验证方式和停止条件。Agent 仍然可以迭代，但只能在你设计好的赛道里活动。

对大多数个人用户和小团队，我建议先从封闭循环开始。至少把下面 6 件事写清楚：

  • 目标：最终要交付什么。
  • 上下文：允许读取哪些资料。
  • 动作：能调用哪些工具、修改哪些范围。
  • 验证：怎样判断每一步和最终结果合格。
  • 预算：最多跑多久、多少轮、多少个 Agent。
  • 停止：什么条件下完成，什么情况必须交还给人。

没有边界的循环更像“放任 Agent 自由发挥”。有边界的循环，才开始接近真正的工程系统。

照着做：先搭一个不花哨的最小循环

理解循环工程，最好的办法不是继续收藏概念，而是找一个小任务亲手跑一遍。

第一步，在项目里新建一份 LOOP.md：

# 当前目标
修复登录状态偶尔丢失的问题。

# 完成条件
- 找到可以稳定复现问题的步骤
- 增加一条失败测试
- 完成修复
- 相关测试全部通过
- 写清根因和改动文件

# 允许范围
- 可以读取整个项目
- 只允许修改登录、缓存和测试相关文件
- 不允许修改生产配置
- 不允许删除文件

# 当前状态
尚未开始

# 下一步
读取登录、缓存和会话相关代码，整理 3 个最可能的原因。

# 尝试记录
暂无

第二步，准备一份简单的项目 Skill，把启动、测试和输出要求写清楚：

# 启动方法
npm install
npm run dev

# 测试方法
npm test
npm run lint

# 完成后必须输出
- 根因
- 修改文件
- 测试结果
- 未解决风险

第三步，把下面这段要求交给 Claude Code、Hermes 或其他能够读写文件的 Agent：

读取 LOOP.md 和项目 Skill。

只执行 LOOP.md 中的“下一步”。
完成后更新“当前状态”“下一步”和“尝试记录”。

如果测试没有通过，不要宣布完成。
如果同一个问题连续失败 3 次，停止并说明阻塞原因。
如果需要删除文件、修改生产配置或扩大修改范围，先询问我。

第四步，换一个会话或子 Agent 做验证。它只读取目标、完成条件、代码差异和测试结果，不参与原来的修改。

第五步，人做最后一个 Checkpoint（检查点）：查看代码差异、测试记录和状态文件，决定接受、继续还是回滚。

这个循环没有多 Agent 大屏，也没有复杂自动化，却已经具备目标、执行、验证、记忆和刹车。先把这条小闭环跑顺，再考虑定时任务、并行 Agent 和连接器。

循环越顺，越要盯紧费用、质量和理解债务

三篇热文都没有把 Loop Engineering 写成“人终于可以不工作了”。恰恰相反，循环越自动，几个风险越容易被放大。

第一是 Token 成本。

每一次重试、每一个子 Agent、每一轮独立验证都要消耗模型用量。循环没有限制时，一个很小的问题也可能反复读取同样的文件，花钱验证已经验证过的结论。

最少要限制 4 项：最长时间、最大轮数、最大并行数和最大预算。

第二是质量。

验证 Agent 也可能判断错误，两个 Agent 也可能共享同样的盲点。能用确定性测试判断的地方，不要只依赖模型评分；架构、权限、数据库迁移和生产发布，仍然应该保留人工检查点。

第三是 Comprehension Debt（理解债务）。

循环每天都在产出代码，人却越来越不知道项目为什么变成这样。短期速度上去了，遇到复杂故障时，团队可能没人说得清核心设计。

Addy 最后给出的提醒很值得保留：搭建循环，但仍然要像一个准备继续承担工程责任的人那样搭，而不是只做那个按下启动按钮的人。

最后提炼：Loop Engineering 会不会成为下一阶段

我认为，Loop Engineering 作为一个统一名称，能不能长期留下还不好说。它与 Harness Engineering（运行框架工程）、Agent Orchestration（Agent 编排）和自主工作流有明显重叠。

但它描述的变化已经很清楚：

阶段

人主要负责什么

Prompt Engineering（提示词工程）

把当前这句话说清楚

Context Engineering（上下文工程）

决定 Agent 应该知道什么

Harness Engineering（运行框架工程）

让一个 Agent 在工具、权限和安全边界里稳定工作

Loop Engineering（循环工程）

让整套系统持续发现、执行、验证、记录并推进下一步

提示词不会消失，人的位置却在往上移动。

以前我们亲自告诉 Agent 每一步做什么；以后，我们会越来越多地负责设计目标、反馈、记忆、预算和停止条件。

大白话总结就是：

提示词让 Agent 做一次事，循环让 Agent 把一件事做完。

真正拉开差距的，可能不再是谁收藏了更多万能提示词，而是谁能搭出一套花费可控、结果可验、失败能停、第二天还能继续的工作闭环。
